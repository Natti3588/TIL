# 2026-08-12

## 学んだこと

### gRPC

RPC + Protocol Buffers + HTTP/2 の組み合わせでできたフレームワーク。
`.proto` を書けば各言語のコードが生成される。通信方式は Unary / Server streaming / Client streaming / Bidirectional の4つ。
バイナリなのでデバッグはしにくいし、ブラウザから直接は呼べない。

### Web APIの設計（2026年時点）

- エラーは Problem Details（RFC 9457）
- 日時は RFC 3339、メソッドとステータスコードは RFC 9110
- 認証は Authorization Code + PKCE
- 廃止は Deprecation / Sunset ヘッダで通知
- ページネーション（カーソル方式）、レートリミット、冪等キーは標準がなく、GitHub や Stripe の実装がデファクト

### OpenAPI（Go）

`openapi` / `info` / `paths` / `components` の4つで骨格ができる。
`operationId` が生成されるGoの関数名になるので必ず書く。
仕様は3.2.0が最新だけど、oapi-codegen が使う kin-openapi は3.0系が安定なので `3.0.3` で書き始めるのが無難。

## わかったこと・気づき

RFCで決まっている領域と、大手の実装に合わせるしかない領域がある。この区別がついたのが一番大きい。

廃止告知をヘッダで返すのは盲点だった。ブログやメールだと、APIを叩いているコードには届かない。

「`.proto` が契約でコードは生成物」という gRPC の考え方は OpenAPI と同じ。別物だと思っていたけど、スキーマ駆動という点では同じことをしている。
公開APIはREST、社内間は gRPC という住み分けらしい。

## まだわからないこと

- Problem Details を Go でどう実装するか（`type` のURI設計あたり）
- 冪等キーのサーバ側の実装。保存先と有効期限、同時リクエストの扱い
- oapi-codegen の生成コードを実際のハンドラにどう繋ぐか
- gRPC を書いたことがないので、まず Unary を1本動かす
