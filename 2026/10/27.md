## REST（Representational State Transfer）

### なぜ REST

今日は Web システムの設計思想（アーキテクチャスタイル）である REST について最近忘れているから。
REST をまとめることで、普段の API 設計に活かせたら良いと考えています。

### REST とは

REST（Representational State Transfer）は、2000 年にロイ・フィールディング博士が提唱した、
分散型ハイパーメディアシステム（Web）の優れた特性を最大限に引き出すためのアーキテクチャスタイルです。
※ RESTful API とはこの REST のアーキテクチャスタイルの原則に従った API のことです。

### REST の主要な原則

REST は一般的に以下の原則の組み合わせによって成り立っています。

#### クライアントとサーバーの役割の分離
クライアントは画面表示やユーザー操作を、サーバーはデータの管理や処理を担当します。
それぞれを独立させることで、機能の改善がしやすくなります

#### ステートレス性
各リクエストに、その要求を理解するために必要な情報を含めます。サーバー側に保存された、過去のやり取りの文脈に依存させないということです。
#### キャッシュ可能
レスポンスを再利用してよいかを明確にし、可能な場合はブラウザや CDN で再利用します。
通信回数とサーバーの負荷を減らせます。

HTTP では `Cache-Control` ヘッダーを使ってキャッシュの指定をします。

#### 統一インターフェース
REST の中心となる原則です。
リソースに対する操作を標準化します。
HTTP メソッドの GET / POST / PUT / DELETE などを使って一貫したリソースの操作をします。

#### 階層化システム
サーバーとの通信の途中に、CDN、プロキシ、ロードバランサなどを配置できるようにします。
各構成要素は、直接やり取りする相手より先にある層の構成を意識せずに通信できるようにします。
例えば、ブラウザ側で API サーバーの台数を意識せずに通信ができれば、サーバー側で台数を増やしたり、負荷分散の構成を変更したりできます。

#### コードオンデマンド（optional）
サーバーから実行可能なコードを送り、クライアントの機能を拡張できます。
例えば CSR では、ブラウザがサーバーから配信された JavaScriptバンドル をダウンロードして実行し、ブラウザ側で画面を描画します。
