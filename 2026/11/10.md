# 2026-11-10

## クラスター化インデックス

昨日MySQLとPostgreSQLの違いを整理したときに出てきた「テーブルそのものが主キーの順に並んでいる」という話を、もう少し詳しく調べました。

**クラスター化インデックス**は、インデックスの中に行のデータそのものが入っているインデックスです。
普通のインデックスは本の索引のように「この値の行はあそこにある」という場所だけを持っていますが、クラスター化インデックスは辞書のように、並んでいる順番そのものがデータの置き場所になっています。

行のデータを置ける場所は1つだけなので、クラスター化インデックスは1つのテーブルに1つしか作れません。

### MySQL（InnoDB）の場合

InnoDBではテーブルが必ずクラスター化インデックスになっていて、何をキーにするかは次の順で決まります。

1. 主キーがあれば主キー
2. 主キーがなければ、最初の `NOT NULL` な `UNIQUE` インデックス
3. どちらもなければ、InnoDBが見えない行IDを勝手に作ってそれを使う

なので「クラスター化インデックスを作らない」という選択肢はありません。
インデックスはB-treeになっていて、一番下の階層（リーフ）に行のデータが丸ごと入っています。

### セカンダリインデックス

主キー以外の列に張ったインデックスは**セカンダリインデックス**と呼ばれます。
InnoDBのセカンダリインデックスのリーフには、行の場所ではなく**主キーの値**が入っています。

例えば `email` にインデックスを張って `WHERE email = ?` で探すと、次の2段階になります。

1. `email` のインデックスをたどって主キーの値を見つける
2. その主キーの値でクラスター化インデックスをたどって行を見つける

B-treeを2回たどるので、主キーで直接探すよりは少し遅くなります。
ただし、欲しい列がセカンダリインデックスの中に全部入っていれば2回目は不要です（**カバリングインデックス**）。
主キーの値は必ず入っているので、`SELECT id FROM users WHERE email = ?` は `email` のインデックスだけで答えが出ます。

### 良いところと気をつけるところ

良いところは次の2つです。

- 主キーで探すとき、インデックスをたどった先にもう行があるので速い
- 主キーが近い行は物理的にも近くに置かれるので、`WHERE id BETWEEN 100 AND 200` のような範囲検索や主キー順の取得が速い

気をつけるところは次の3つです。

- ランダムな値を主キーにすると、INSERTのたびに途中のページに割り込むことになる。ページがいっぱいだと2つに分ける処理（**ページ分割**）が起きて、遅くなるうえにスカスカのページが増える
- 主キーの値がすべてのセカンダリインデックスにコピーされるので、主キーが長いとインデックス全部が大きくなる
- 主キーの値を `UPDATE` すると行の置き場所が変わるので重い

昨日の「MySQLでUUIDv4を主キーにすると遅い」という話は1つ目の理由でした。
UUIDv7は先頭が時刻なので、連番と同じようにほぼ末尾に追加されていきます。
9日のテーブル設計で聞いた「主キーは意味のない、変わらない値にする」という話も、3つ目を考えるとMySQLでは性能の面でも理にかなっているとわかりました。

### PostgreSQLの場合

PostgreSQLにはクラスター化インデックスがありません。
行は**ヒープ**という順番を気にしない場所に置かれていて、主キーのインデックスも含めて、すべてのインデックスが行の場所（何ページ目の何番目か）を指しています。
InnoDBの言い方でいえば、全部がセカンダリインデックスのような作りです。

| | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| 行の置き場所 | 主キーのB-treeのリーフ | ヒープ（順番なし） |
| 主キーのインデックスが持つもの | 行そのもの | 行の場所 |
| 他のインデックスが持つもの | 主キーの値 | 行の場所 |
| 主キーで探す | B-treeを1回たどる | B-treeを1回 + ヒープを見る |
| 他のインデックスで探す | B-treeを2回たどる | B-treeを1回 + ヒープを見る |
| ランダムな主キーでのINSERT | テーブル本体でページ分割が起きる | テーブル本体は空いている場所に置くだけ |

紛らわしいのが、PostgreSQLにも `CLUSTER` というコマンドがあることです。
これは指定したインデックスの順にテーブルを**その時点で1回だけ**並べ直すもので、そのあとINSERTやUPDATEをされた行は順番どおりには置かれません。
実行中はテーブル全体がロックされるので、気軽に使うものでもないそうです。

PostgreSQLでもランダムなUUIDの影響がゼロというわけではなく、主キーのインデックス自体はB-treeなので、そちらではページ分割が起きます。
ただテーブル本体は並べ替えないので、InnoDBほどは影響が大きくないという理解です。

同じ「主キーにインデックスがある」でも、MySQLは「主キーの順にデータが置いてある」、PostgreSQLは「データとは別に主キーの索引がある」で、意味がかなり違うことがわかりました。
