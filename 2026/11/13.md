## セカンダリインデックスは B+Tree を2回たどる（InnoDB）

InnoDB では、主キー以外のインデックス（**セカンダリインデックス**）のリーフノードに入っているのは「インデックスを張ったカラムの値」と「**主キーの値**」です。
行そのものも、行の場所も入っていません。

なので `SELECT * FROM users WHERE name = 'サトウ'` を実行すると、次の順で読みます。

1. `name` のインデックスをたどって、主キーの値を取り出す
2. その主キーで、クラスタ化インデックスをルートノードからたどり直して、行を取り出す

図で数えると、セカンダリインデックスの深さ2とクラスタ化インデックスの深さ3を足して5ページでした。
PostgreSQL はリーフノードがヒープの行の場所を直接指しているので、同じ検索が3ページで済みます。
主キーの検索では InnoDB の方が少なかったので、逆の結果です。
InnoDB は主キーの検索を速くする代わりに、それ以外のインデックスで余分に読む、という引き換えだと理解しました。

### なぜ行の場所ではなく主キーの値を持つのか

クラスタ化インデックスでは、行の挿入などでページが分割されて、行の場所が変わる可能性があるからです。
場所は変わっても主キーの値は変わらないので、そちらを持っています。

### 主キーは短いほうがよい

ここは口頭で説明できませんでした。
主キーが長いと、その分セカンダリインデックスのリーフノードに入っている主キーの値も大きくなる、というのを知らなかったからです。

計算してみると差がわかりました。1ページを 16,000 バイト、`name` を 12 バイトとすると、

- 主キーが 4 バイトの整数：1エントリ 16 バイト → 1ページに 1,000 個
- 主キーが 36 バイトの文字列：1エントリ 48 バイト → 1ページに約 333 個

同じ行数でもページが約3倍必要になります。
しかも、すべてのセカンダリインデックスが行ごとに主キーの値を持つので、インデックスが5つあれば5回上乗せされます。

## カバリングインデックス

**カバリングインデックス**は、クエリが必要とするカラムを全部持っているインデックスです。
特別な種類のインデックスではなく、「このクエリには、このインデックスだけで足りる」という関係の呼び名です。

`SELECT *` を `SELECT id` に変えると、`name` のインデックスのリーフノードに主キーの `id` が入っているので、そこで答えがそろいます。
クラスタ化インデックスをたどり直す2回目の走査が要らなくなって、5ページが2ページになりました。

| SQL（`WHERE name = …`） | InnoDB で読むページ | 理由 |
|---|---|---|
| `SELECT id, name` | 2 | どちらもセカンダリインデックスにある |
| `SELECT city` | 5 | `city` はインデックスにないので、行を取りに行く |
| `SELECT *` | 5 | 全部のカラムを持つインデックスはふつう作らない |

`SELECT *` を避けて必要なカラムだけを書く理由の1つが、これだとわかりました。
セカンダリインデックスが主キーの値を持つことは、さっきは弱点の原因でしたが、ここでは「主キーが最初からカバーされている」という利点になっています。

### PostgreSQL の Index Only Scan と可視性マップ

PostgreSQL では、インデックスだけで答えを返す動きを **Index Only Scan** と呼びます。
ここは口頭で説明できず、「なぜ Index Only Scan がヒープを読むことがあるのか」にも答えられませんでした。

- 行が今のトランザクションから見えるかどうかの情報は、ヒープにしかない（インデックスにはない）
- そこで、ヒープのページごとに「全部の行が全員から見える」という印を持っている。これが**可視性マップ**
- ビットが立っていればヒープを読まない。立っていなければヒープを読んで確かめる

PostgreSQL の `name` のインデックスには `id` が入っていないので、`SELECT id` をカバーしたければ `CREATE INDEX … ON users (name) INCLUDE (id)` のように足す必要があります。

## EXPLAIN で確かめる（Docker）

Docker で MySQL 8.4 と PostgreSQL 17 を動かして、10万行の `users` テーブルで `EXPLAIN` を実行するレッスンをやりました。
問題は全部は解けませんでした。もう一度やり直します。

見るところだけ、まとめておきます。

| 確かめたいこと | MySQL | PostgreSQL |
|---|---|---|
| どのインデックスを使うか | `key` の欄 | 1行目の `using …` |
| 全部読んでいないか | `type` が `ALL` | `Seq Scan` |
| インデックスだけで答えたか | `Extra` に `Using index` | `Index Only Scan` |
| 実際にヒープを読んだ回数 | — | `EXPLAIN ANALYZE` の `Heap Fetches` |

`EXPLAIN` は実行計画を表示するだけで、SQL そのものは実行しません。
PostgreSQL の `EXPLAIN ANALYZE` は実際に実行します。
可視性マップのビットは `VACUUM` だけが立てて、ページのデータを変更すると下りるそうです。

## まだわからないこと

- `EXPLAIN` のレッスンで解けなかった問題（MySQL の `type` と `Extra` の読み方、`Heap Fetches` の数え方）
- 可視性マップ。`VACUUM` の前後で `Heap Fetches` が変わるところを、自分で実行して確かめたい
- 複合インデックス `(name, city)` は `WHERE city = …` で使えるのか
- 主キーを UUID にすると、挿入とページ分割で何が起きるのか
