## EXPLAIN でクエリの実行のされ方を確認する

SQL の前に `EXPLAIN` を付けると、そのクエリをどう実行するつもりか（実行計画）を見られます。
Docker で MySQL 8.4 と PostgreSQL 17 を動かして、10万行の `users` テーブルで試しました。

```sql
-- MySQL（\G を付けると縦に並んで読みやすい）
EXPLAIN SELECT id FROM users WHERE name = 'name0052'\G

-- PostgreSQL
EXPLAIN SELECT name FROM users WHERE name = 'name0052';
EXPLAIN ANALYZE SELECT name FROM users WHERE name = 'name0052';
```

`EXPLAIN` は計画を表示するだけで、クエリそのものは実行しません。
PostgreSQL の `EXPLAIN ANALYZE` は実際に実行して、かかった時間なども出してくれます。

### MySQL は key → Extra の順に見る

欄が12個も出てきて最初はどこを見ればいいのかわかりませんでしたが、見るのは3つだけでした。

| 出力 | 何をしているか |
|---|---|
| `key: NULL`、`type: ALL` | インデックスを使わず、テーブルを全部読む |
| `key: PRIMARY` | 主キー（クラスタ化インデックス）で探す |
| `key: idx_name`、`Extra: NULL` | `name` のインデックスで探したあと、行を取りに行く |
| `key: idx_name`、`Extra: Using index` | `name` のインデックスだけで答えを返す |

勘違いしやすいのは `Extra: NULL` です。
「インデックスを使っていない」という意味に見えますが、「補足することがない」というだけでした。
インデックスを使ったかどうかは `key` の方で決まります。
`Using where` も `Using index` と名前が似ているだけで別物でした。

`SELECT *` を `SELECT id` に変えるだけで `Extra` が `NULL` から `Using index` に変わります。
`name` のインデックスに主キーの `id` も入っているので、行を取りに行かなくて済むからです。

### PostgreSQL は1行目と Heap Fetches を見る

PostgreSQL は1行目に読み方がそのまま書いてあります。

- `Seq Scan`：全部読む
- `Index Scan using idx_name`：インデックスで探して、ヒープから行を取る
- `Index Only Scan using idx_name`：インデックスだけで答える

`EXPLAIN ANALYZE` だと `Heap Fetches` という行が出て、Index Only Scan の途中で実際にヒープを読んだ回数がわかります。
`VACUUM` する前は 10（見つかった10行すべて）で、`VACUUM users;` のあとは 0 になります。
Index Only Scan という名前でも、`VACUUM` していないとヒープを読んでしまうようです。
