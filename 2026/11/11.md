# 2026-11-11

## クラスター化インデックス（基礎から）

昨日まとめたクラスター化インデックスは用語が多くてわからなかったので、前提になる話から順番に整理し直しました。

### 1. データは「箱」に入れて保存されている

テーブルの行は、ディスクの上に1行ずつバラバラに置かれているわけではありません。
**ページ**という決まった大きさの箱（MySQLは16KB、PostgreSQLは8KB）に、何行かずつまとめて詰められています。

DBがデータを読むときも1行ずつではなく、この箱を丸ごと1つ取り出します。
なので「探している行を見つけるために、箱をいくつ開けたか」が速さに直結します。

例として、次のような会員テーブルで考えます。

| id  | name | email                 |
| --- | ---- | --------------------- |
| 1   | 佐藤   | sato@example.com      |
| 2   | 鈴木   | suzuki@example.com    |
| 3   | 高橋   | takahashi@example.com |
| ... | ...  | ...                   |

### 2. インデックスがないと、全部の箱を開けることになる

`WHERE id = 5000` で探すとき、行がどの箱に入っているか何の手がかりもなければ、最初の箱から順番に全部開けて確かめるしかありません。
100万行あれば100万行ぶん見ることになります。

### 3. インデックスは「本の索引」

**インデックス**は、本の巻末にある索引と同じものです。

- 索引は「キーワード → 何ページ目」の一覧で、キーワードの順に並んでいる
- 並んでいるので、全部読まなくても目的のキーワードをすぐ見つけられる
- 見つけたら、書いてあるページを開きに行く

DBのインデックスも「値 → その行が入っている箱の場所」の一覧で、値の順に並んでいます。
並んでいるおかげで、辞書を引くときのように「真ん中を開いて、前か後ろか決めて、また真ん中を開く」を繰り返せば、100万件あっても数回で見つかります。

（この「何段かに分けて絞り込んでいく形」のことを **B-tree** と呼びます。一番下の段が昨日出てきた**リーフ**で、そこに探していたもの（ここでは行の場所）が書いてあります。）

ここまでで大事なのは、**普通のインデックスは「場所のメモ」で、データ本体は別のところにある**ということです。

### 4. クラスター化インデックスは「辞書」

インデックスには、もう1つの作り方があります。
索引で場所を調べてから本文を見に行くのではなく、**データ本体そのものを、キーの順番に並べてしまう**方法です。

- 普通のインデックス：**本の索引**。索引で「120ページ」と調べてから120ページを開く
- クラスター化インデックス：**国語辞典**。言葉があいうえお順に並んでいるので、引いた場所にもう説明が書いてある

この国語辞典の形が**クラスター化インデックス**です。
会員テーブルなら、行そのものが `id` の順番に箱へ詰められていて、`id = 5000` を探すと、たどり着いた場所にもう行のデータが入っています。
場所のメモを読んでから取りに行く、という1手間がありません。

### 5. クラスター化インデックスは1つのテーブルに1つだけ

辞書は「あいうえお順」に並べたら、同時に「画数順」には並べられません。
同じように、データ本体を並べられる順番は1通りだけなので、クラスター化インデックスは1つのテーブルに1つしか作れません。

MySQL（InnoDB）では、この並び順に**主キー**が使われます。
つまりMySQLのテーブルは、作った時点で必ず「主キーの順に並んだ辞書」になっています。

### 6. 主キー以外で探すときは2回引く

会員テーブルで `WHERE email = 'suzuki@example.com'` のようにメールアドレスで探したいときは、`email` に普通のインデックスを張ります。
主キー以外の列に張るインデックスなので、**セカンダリインデックス**（2番目のインデックス）と呼びます。

MySQLのセカンダリインデックスには、行の場所ではなく**主キーの値**がメモされています。
なので探す流れは2段階になります。

1. `email` のインデックスで `suzuki@example.com` を探す → 「id は 2」とわかる
2. 主キーの辞書で `id = 2` を引く → 行のデータが見つかる

「名前で探して会員番号を調べ、会員番号で名簿を引く」という感じです。
主キーで直接探すより1回多く引くので、少しだけ遅くなります。

### 7. 主キーの選び方が速さに関わる

辞書のようにきっちり順番に並んでいるので、新しい行を追加するときは「順番どおりの位置」に入れる必要があります。

- **連番**（1, 2, 3, ...）：新しい行はいつも一番後ろに足すだけ。最後の箱がいっぱいになったら新しい箱を足せばいい
- **ランダムな値**（UUIDv4 など）：新しい行が途中のどこかに割り込む。割り込む先の箱がいっぱいだと、箱を2つに分けて詰め直す（**ページ分割**）必要がある

ページ分割は手間がかかるうえに、半分しか入っていない箱が増えていきます。
9日に聞いた「MySQLでランダムなUUIDを主キーにすると遅い」という話は、これが理由でした。
UUIDv7は先頭が時刻なので、新しいものほど後ろに並び、連番と同じように一番後ろに足していけます。

### 8. PostgreSQLはこの仕組みを使っていない

PostgreSQLのテーブルは辞書ではなく、行は空いている箱に順番を気にせず入れられます（この置き場所を**ヒープ**と呼びます）。
主キーも含めて、インデックスはすべて「本の索引」の形で、行の場所をメモしているだけです。

| | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| テーブルの形 | 主キー順の辞書 | 順番を気にしない置き場所 |
| 主キーで探す | 引いた場所に行がある | 索引で場所を調べて取りに行く |
| 主キー以外で探す | 索引で主キーを調べて、辞書を引く | 索引で場所を調べて取りに行く |
| ランダムな主キーの影響 | 大きい（テーブル本体で割り込みが起きる） | 小さめ（割り込みは索引の中だけ） |

### まとめ

- データは箱（ページ）単位で読み書きされる。開ける箱が少ないほど速い
- 普通のインデックスは本の索引。場所のメモで、データ本体は別にある
- クラスター化インデックスは国語辞典。データ本体がキーの順に並んでいる
- 並べ方は1通りしかないので、1テーブルに1つだけ。MySQLでは主キーがそれになる
- 主キー以外で探すと「主キーを調べてから辞書を引く」の2回になる
- 途中に割り込まないように、主キーは連番かUUIDv7にする

## まだわからないこと

- 箱1つに何行くらい入るのか（行の大きさで変わるはず）
- 主キーを作らずにMySQLのテーブルを作ったら、何の順番で並ぶのか
- 「2回引く」のを避ける方法（昨日出てきたカバリングインデックスがそれらしい）
