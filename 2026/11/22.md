## HTTP のハンドラのエラーハンドリング

API のハンドラで、下の層から返ってきたエラーをどう返すかの考え方をまとめました。

### 判断の仕方

エラーごとに、原因がクライアントの側にあるかサーバーの側にあるかを考えます。
クライアントの側なら 4xx で理由を返し、サーバーの側なら 5xx にします。
5xx の多くは 500 です。

| エラーの例         | 原因     | 返すもの |
| ------------- | ------ | ---- |
| 入力の形式が正しくない   | クライアント | 400  |
| ログインしていない     | クライアント | 401  |
| 権限がない         | クライアント | 403  |
| 指定したものがない     | クライアント | 404  |
| データベースにつながらない | サーバー   | 500  |

### ステータスはハンドラで決める

サービスやリポジトリは HTTP を知らないので、「見つからない」「入力が不正」のような意味だけをエラーで返します。
Go なら `errors.New` で `ErrNotFound` のようなセンチネルエラーを作り、ハンドラで `errors.Is` を使って見分けます。
途中の層でエラーを包むときは `fmt.Errorf` の `%w` を使います。
`%v` で包むと、`errors.Is` で見分けられなくなります。

同じエラーでも、何が見つからないかで返すステータスが変わります。
URL で指定したものがないなら 404 です。
ログイン中のユーザー自身がいないなら、セッションが無効なのと同じなので 401 にします。

### 見分けたもの以外は 500

想定したエラーを先に見分けて `return` し、残りはすべて 500 にします。

```go
if err != nil {
	if errors.Is(err, ErrNotFound) {
		// 404 を返して return
	}
	logger.Error("記事の取得に失敗", "error", err)
	// 500 を返して return
}
```

エラーの中身には SQL やファイルのパスが入ることがあるので、500 の応答には決まった文言だけを返します。
原因はログに残します。
応答の途中で失敗しても原因が残るように、ログは応答より先に書きます。

### ログの文言は失敗した範囲に合わせる

1つの処理に複数の手順があると、どこで失敗したかで状態が変わります。
保存してから読み直す処理で読み直しに失敗したとき、ログに「保存に失敗」と書くと、実際は保存できているので事実と食い違います。
処理全体を指す言い方にしておき、詳しい原因はエラーの中身で見ます。
